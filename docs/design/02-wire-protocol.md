# 线路协议与 codec

本文定义 gate 在 TCP 字节流（或 WebSocket 二进制消息）之上的分帧格式，以及唯一的
解析实现 `codec` 的规格。

这一层是整个库里**唯一面对不可信输入**的地方：对端可以是任何东西，包括一个专门
构造畸形字节的攻击者。因此本文的组织方式是「格式 → 校验规格 → 攻击面分析」，
校验顺序本身就是规格的一部分。

## 为什么自己定分帧

候选方案与被否掉的理由：

| 方案 | 为什么不用 |
| --- | --- |
| 4 字节定长长度前缀 | 小消息占比极高的场景下每条白付 2 字节。1M msg/s 就是 2MB/s 纯浪费，更要命的是它稀释合包密度 |
| varint 长度（protobuf delimited） | 长度不定长 ⇒ 无法在读到固定字节数后就知道帧边界，解析要循环；且没有地方放标记位 |
| 复用 WebSocket 分帧 | 只在 WS 传输下存在。裸 TCP 仍要一套，等于两套语义（上一版的教训） |
| 带类型字段的自描述头 | 类型是业务的事，不是网关的事。gate 不解析 payload |

选定的形状：**长度与标记位共享同一个首字节，小消息 2 字节头、大消息 4 字节头。**

标记位必须和长度在一起，因为解析器读到第一个字节就要知道「这一帧要不要解密/解压/展开」，
而不是读完 payload 再回头查一张边表。

## 帧头

### 布局

```
size < 4096（绝大多数消息）：2 字节

  bit  15  14  13  12  11 ─────────────── 0
      ┌───┬───┬───┬───┬─────────────────────┐
      │ m │ z │ c │ e │      size (12)      │
      └───┴───┴───┴───┴─────────────────────┘
        0

size >= 4096：4 字节

  bit  15  14  13  12  11 ─────────────── 0   15 ──────────────────── 0
      ┌───┬───┬───┬───┬─────────────────────┬────────────────────────┐
      │ m │ z │ c │ e │   size 高 12 位     │      size 低 16 位     │
      └───┴───┴───┴───┴─────────────────────┴────────────────────────┘
        1
```

大端序。`size = 高12 × 65536 + 低16`。

| 位 | 名字 | 含义 |
| --- | --- | --- |
| `m` | more header | 头是 4 字节而不是 2 字节 |
| `z` | compressed | payload 是 zstd 压缩后的字节 |
| `c` | compound | payload 是若干条子消息拼接而成 |
| `e` | encrypted | payload 是密文 |

### 可表达范围

| | |
| --- | --- |
| 2 字节头 | `size ∈ [0, 4095]` |
| 4 字节头 | `size ∈ [4096, 2²⁸−1]`（约 256MB） |
| 协议上限 `maxMessageSize` | **32MB**，远小于 2²⁸−1 |

上限取 32MB 而不是顶到 2²⁸−1，是为了给「长度字段溢出」留一整段安全余量：
一旦有人把 ≥ 2²⁸ 的长度交给编码器，高位会溢进首字节的 `m`/`z`/`c`/`e`，
**长度和标记会被同时改错，而且收发两端都察觉不到**。

实现必须有一条编译期断言把这个不变式钉死：

```go
// maxMessageSize 必须严格小于 header 能表达的上限，
// 否则下面这个负常量转 uint 会直接编译失败。
const _ = uint(maxHeaderLen - 1 - maxMessageSize)
```

`Limits.MaxMessage` 是在这个协议上限之内的、每连接可再收紧的值。

### 规范编码（canonical form）

**`m = 1` 当且仅当 `size >= 4096`。**

也就是说，一条 100 字节的消息**只有一种**合法编码。收到 `m = 1` 但 `size < 4096`
的帧一律按协议违规处理。

上一版没有这条规则，于是同一条消息有两种线路表示。这是 parser differential 的经典
温床：只要链路上出现第二个解析者（LB、审计代理、抓包分析、另一种语言实现的客户端），
两边对「这是不是同一条消息」的判断就可能不一致。**能有唯一表示就不要留两种。**

### 扩展空间

强制规范编码之后，`m = 1 && 高12 == 0 && 低16 < 4096` 这段编码变成**不可达**，
共 4096 个取值。它是**唯一预留的扩展点**：将来需要版本号、新标记位或新帧类型时，
从这里开辟，老实现会把它当协议违规拒掉——这正是我们要的行为（明确失败，不是
静默误解）。

除此之外，帧头里**没有任何保留位**：4 个标记位全部用满，12 位长度也全部用满。
这是刻意的取舍——2 字节头的价值就来自这种紧凑，留保留位就要么牺牲长度范围，
要么把头撑到 3 字节。扩展路径由上面那段不可达编码承担。

## 帧体：三个变换与它们的顺序

```
|-h-|──────────── frame payload ────────────|
    |──────── 解密后 ────────|                        e = 1
    |──────────── 解压后 ────────────|                z = 1
    |-h-|─msg─|-h-|─msg─|-h-|─msg─|                  c = 1
```

**编码顺序（发送侧）：**

```
业务消息
  → [c] 拼成 compound body（每条子消息带自己的 2/4 字节头）
  → [z] 整体 zstd 压缩          ← 压缩发生在拼包之后
  → [e] Seal
  → 写外层帧头（长度 = 最终字节数）
  → writev
```

**解码顺序（接收侧）严格相反：**

```
读帧头 → 长度与标记校验
  → [e] Open
  → [z] 解压（带输出上限）
  → [c] 迭代切分成子消息
  → 逐条交给业务
```

### 为什么是「先压缩后加密」

反过来（先加密后压缩）压缩率会退化到 1.0——密文的熵接近满，压不动。
这是所有做压缩+加密的协议的共识顺序（TLS 也是这个顺序）。

它带来一个已知的侧信道，见[攻击面分析](#压缩侧信道crime-类)。

### 为什么是「先拼包后压缩」而不是逐条压缩

这是这个协议最主要的价值点。

100 条相似的小消息拼成 30KB 再压一次，压缩比远高于压 100 次——zstd 可以跨消息
复用上下文（同样的字段名、同样的枚举值、同样的结构），而逐条压缩时每条都要从
零开始建字典，几十字节的消息往往越压越大。

`Outbound.Dict` 是这条结论的补充：挂一个用协议样本训出来的字典之后，**单条**小消息
也能有好压缩比，不必依赖攒够体积。两者可以叠加。

### 各变换的开关是独立的

`c` 和 `z` 由各自的配置项决定，互不牵连：

- 大量小消息 → 该合包但不值得压缩（`MaxCluster > 0`，`CompressThreshold <= 0`）：
  合包本身就省下系统调用和小 TCP 段。
- 单条大消息 → 该压缩但没得合（`CompressThreshold > 0`）。

## compound

```
compound payload = Σ ( 子帧头 + 子 payload )
```

**子消息的标记位必须全为 0**（`z = 0, c = 0, e = 0`）。子帧头实际只用到 `m` 和长度。

这条约定不是风格问题，它带来两个结构性后果：

1. **不存在嵌套。** 展开 compound 时用一个 `allow = 0` 的子策略去解析，任何带标记的
   子消息（包括另一个 compound）都会在校验阶段被拒掉。因此展开是**迭代**而不是递归，
   结构上不存在栈深度问题，也就不存在「构造 10 万层嵌套打爆栈」这种攻击。
2. **子消息之间互不可见。** 子 payload 借用父 buffer 的底层数组，实现必须用三索引
   切片 `src[a:b:b]` 把容量封在末尾——否则一个 sink 里的 `append` 就能悄悄覆盖掉
   紧随其后的兄弟消息。这是免费的，而且让「互不可见」成为结构性事实，
   不依赖每个调用点各自记得拷贝。

**compound body 必须正好切分干净。** 切不干净（剩下不足一个完整子帧的残留字节）
说明对端构造有误，按协议违规处理——而不是「再等等就好」。compound 是一个已经完整
收齐的 payload，不存在「后续数据」。

## 策略：allow 掩码

同一份解析实现被三个角色复用，差异只体现为一个字段：

| 角色 | `allow` | 含义 |
| --- | --- | --- |
| 服务端解析上行 | `e` | 只接受对端加密；上行压缩与合包一律拒绝并断开 |
| 客户端解析下行 | `z \| c \| e` | 服务端下行三种都可能用 |
| compound 子消息 | `0` | 子消息不得携带任何标记 |

`m` 是结构性标记，任何策略下都允许。

上一版这份 wire protocol 被三处代码分别解析（TCP 服务端、WebSocket 服务端、客户端），
三处对 `z`/`c`/`e` 采取了三种不同的策略，于是**同一个协议缺陷会在不同传输上以不同
形式出现**——最严重的一处是 WS 服务端用了一个只认 `e`、把 `z`/`c` 默默忽略掉的私有
解析器，客户端只要置一位 flag，就能把压缩后的原始字节或未展开的 compound 直接塞给
业务层。一份实现 + 一个策略字段从根上消除这类分歧。

### 为什么服务端不接受上行压缩与合包

**收益不存在：**

- 合包：客户端本来就可以把多条消息写进同一个 `write` 调用，一个 TCP 段里塞几条
  完整帧，服务端一次读事件就能全部消费。**协议层的合包对上行没有额外收益**——
  它省的是发送方的系统调用，而客户端只有一条连接，本来就没有那个开销。
  WebSocket 下更是如此：多条 gate 帧本来就装在同一个 WS 二进制消息里。
- 压缩：上行以小消息（输入、指令）为主，几十字节压不动。

**代价很实在：**

- 接受上行压缩 ⇒ 服务端必须常驻 zstd 解码器（每 loop 一个，内存），并且**引入解压
  炸弹攻击面**：一个几 KB 的帧可以解出数百 MB。
- 接受上行 compound ⇒ 引入展开循环的攻击面（虽然迭代展开已经堵住了嵌套，
  但仍要为「一个 32MB 的 compound 里塞 1600 万条空消息」这种放大做好准备）。

不接受的结果是：**服务端根本不存在解码器**，这两条攻击面从代码里消失，
而不是靠上限参数去防守。这是这份协议里性价比最高的一个决定。

## 校验规格

解析一个帧的顺序是规格的一部分。实现必须按这个顺序，**因为每一步都保护着后面的步骤**：

```
1. 可读字节 < 2                      → 数据不足，等待（可重试）
2. 读 2 字节头，取出 m/z/c/e 与 size12
3. m = 1 且可读字节 < 4              → 数据不足，等待（可重试）
4. m = 1 → 读第 3、4 字节，拼出完整 size
5. 规范编码：m = 1 且 size < 4096    → 协议违规
6. size > codec.maxMessage           → 协议违规      ← 必须早于任何按长度切片/分配
7. 标记位不在 allow 之内             → 协议违规
8. 配了 Cipher 但 e = 0              → 协议违规      ← 见「降级攻击」
9. 可读字节 < header + size          → 数据不足，等待（可重试）
10. 切出 payload（三索引切片封住 cap）
────────── 以上为 parse，以下为 deliver ──────────
11. e = 1 → Open；失败                → 协议违规
12. z = 1 → 解压，带输出上限；失败或超限 → 协议违规
13. c = 1 → 迭代展开，子策略 allow = 0
14. 逐条交给业务
```

第 6 步的位置是硬要求：**长度校验必须早于任何按长度进行的分配或切片**。
否则对端只要谎报一个长度，就能让我们立刻申请那么多内存——一个 4 字节的头
换服务端 32MB，放大比 800 万倍。

第 8 步是这一版新增的，见下。

## 攻击面分析

### 解压炸弹

**服务端：不存在。** 上行不接受 `z`，连解码器都没有。

**客户端**（gate 自带的测试客户端，以及任何第三方实现）必须设两道闸：

1. 解码器构造时设 `WithDecoderMaxMemory(maxDecompressed)`——不设的话
   klauspost/compress 默认允许 64GB。
2. 解压完成后**再显式校验一次**输出长度。两道闸看起来冗余，但上限可能因构造方式
   不同而失配，而放大攻击的代价太低，值得重复校验。

### compound 嵌套 / 栈溢出

**结构上不可能。** 子策略 `allow = 0` 让任何嵌套 compound 在校验阶段就被拒，
展开是迭代的。

### 兄弟消息互相覆盖

三索引切片封住 cap，见 [compound](#compound)。

### 长度字段溢出进标记位

编译期断言 + 发送侧在写头之前再判一次。任何越界都宁可关连接，也不能写一个
「长度和标记同时错、两端都察觉不到」的帧上线路。

### 降级攻击：清掉 `e` 位

帧头**不在**加密的认证范围内（AEAD 的 AAD 里没有它），所以一个能改字节的中间人
可以翻转标记位。逐位分析后果：

| 翻转 | 后果 |
| --- | --- |
| `z` 0→1 | 接收方尝试解压明文 → zstd 失败 → 关连接。**可检测** |
| `c` 0→1 | 接收方尝试切分 → 几乎必然切不干净 → 关连接。**可检测** |
| `m`、长度 | 帧边界错位 → 后续解析失败 → 关连接。**可检测** |
| **`e` 1→0** | 接收方**不解密**，把密文当明文原样交给业务层。**这是唯一一个静默的** |

所以校验规格第 8 步：**只要连接配置了 `Cipher`，就要求每一个入站帧都带 `e = 1`，
否则按协议违规关闭。** 一次布尔判断，把唯一那条静默路径堵死。

上一版没有这条规则：`if f.e { decrypt }`，`e = 0` 的帧即使在配了 cipher 的连接上
也会被当明文投递。

> **不把帧头放进 AAD 的理由。** 那需要 `Cipher` 接口带上 `aad` 参数，而长度字段
> 依赖 seal 之后的字节数（循环依赖），只能把标记位单独拎出来做 AAD——为 4 个 bit
> 增加一个接口参数、并要求所有实现正确处理它，不划算。
> 更重要的是**定位问题**：gate 的 `Cipher` 是防嗅探/防外挂的纵深防御，
> **不是**用来对抗主动中间人的——那是 TLS 的职责，而 gate 明确要求前置 TLS 终结
> （见 01 的非目标）。在这个定位下，「可检测」对三种翻转已经足够，
> 剩下那一种用一次布尔判断解决。

### 压缩侧信道（CRIME 类）

先压缩后加密意味着**密文长度泄漏了明文的可压缩性**。经典利用方式是：攻击者能让
自己控制的内容和一个秘密进入同一个压缩单元，然后通过观察长度来逐字节猜测秘密。

gate 的暴露面：

- **独立帧**：一条消息一个压缩单元。攻击者要控制这条消息的一部分、同时它又含有
  秘密——取决于业务，gate 管不了。
- **compound**：一个合并帧里有多条消息，它们**同属一个压缩单元**。如果同一批里既有
  攻击者可影响的内容（例如自己发出去又被回显的聊天），又有秘密（例如一次性令牌），
  长度就成了 oracle。

对策（写给使用者）：

1. 敏感消息用 `SendPlain` —— 它保证明文独立帧，不进压缩、不进合包。
2. 或者对该连接关掉压缩（`CompressThreshold <= 0`），只保留合包。

gate 不自作主张地替业务判断什么是敏感数据，但把这个取舍写在这里，并且提供了
一个成本为零的规避接口。

### 空消息放大

`size = 0` 是合法的（业务可能用它做 ping）。但它在计量上不是零成本，见下。

## 与 AEAD 的关系

`Cipher.Overhead() > 0` 时密文比明文长，这对帧格式有两个影响：

1. **帧头写的是最终线路字节数**，也就是 seal 之后的长度。因此编码时**必须先 seal
   再写头**，不能像长度保持的流式密码那样先占位再原地加密。
2. **`Limits.MaxMessage` 约束的是线路长度**（我们必须缓冲的那个数）。
   `Open` 之后的明文只会更短，所以不需要第二重检查。

compound 的子帧头描述的是**明文**长度：compound body 在被切分之前已经完成
`Open` 和解压，切分时看到的就是明文。

## 计量口径

**所有的队列计量、预算扣减、分组累加都必须用 `frameSize = payload + header`，
而不是 `len(payload)`。**

一条空消息的 `len` 是 0，但它在线路上仍占 2 字节头，在内存里仍占一个队列条目。
按 `len` 计量的后果：

- `Send([]byte{})` 循环可以在 `MaxBuffer` 已设的情况下把队列涨到 OOM
  （`queued` 永远是 0，`ErrSendQueueFull` 永远不触发）。
- 合包会把任意多条空消息收进同一个 compound——每条都在 body 里贡献 2 字节子头，
  最终帧可以远远超过 `MaxCluster`，甚至越过协议上限被对端拒收。

`MaxCluster` 计量的也是 compound body（含子头），因为**那正是最终写进外层帧头
长度字段的那个数**。两者必须是同一个数。

## 错误分类

解析只有两种结果，实现必须让它们在类型上无法混淆：

| 结果 | 含义 | 调用方行为 |
| --- | --- | --- |
| `ok = false, err = nil` | 数据还不足以构成一个完整帧 | 保留字节，等下一次读事件 |
| `err != nil` | 对端违反协议 | **关闭连接**，`OnClose(ErrProtocol)` |

**这是唯一一种可重试的返回。** 任何其他错误都不给「再等等」的机会——协议违规意味着
对端的实现或意图有问题，继续读它的字节没有意义。

具体错误值（都会被包进 `ErrProtocol`）：

| | |
| --- | --- |
| `ErrMaxMessageSize` | 长度超过 `maxMessage` |
| `ErrNonCanonicalHeader` | `m = 1` 但 `size < 4096` |
| `ErrFlagNotAllowed` | 标记位不在 `allow` 之内 |
| `ErrCipherRequired` | 配了 Cipher 却收到 `e = 0` 的帧 |
| `ErrDecryptFailed` | `Open` 返回错误 |
| `ErrDecompressLimit` | 解压输出超过上限 |
| `ErrTrailingBytes` | compound 切不干净 |

## codec 的内部形状

（内部类型，不在公共 API 里，但 03/04/05 都依赖它，所以在这里定死。）

```go
// codec 描述一侧对入站帧的解析策略。零值不可用。
type codec struct {
	maxMessage      int  // payload 字节上限
	maxDecompressed int  // 解压输出上限；<= 0 表示不接受压缩帧
	allow           byte // 允许对端设置的标记位
	requireEncrypt  bool // 连接配了 Cipher ⇒ 每帧必须 e = 1
}

func serverCodec(maxMessage int) codec          // allow = maskE
func clientCodec(maxMessage, maxDecomp int) codec // allow = maskZ|maskC|maskE
func (c codec) subCodec() codec                  // allow = 0

// parse 从 src 头部定位一个完整帧，不做任何解密/解压/展开。
// payload 借用 src 的底层数组（三索引切片），生命周期由调用方负责。
func (c codec) parse(src []byte) (f frame, n int, ok bool, err error)

// deliver 完成 解密 → 解压 → 展开 的全过程，逐条交给 sink。
// owned = true 表示这块内存是本次解码新分配的，sink 可以直接接管。
func (c codec) deliver(f frame, ci Cipher, dec *zstd.Decoder,
	sink func(msg []byte, owned bool) error) error
```

两个约束：

- **`parse` 与 `deliver` 分开**，因为 `parse` 要在「数据够不够」这个问题上给出答案，
  而 `deliver` 只在数据够了之后跑。合成一个函数会让「可重试」和「协议违规」这两种
  语义纠缠在一起。
- **`sink` 拿到的切片只在本次调用期间有效。** 这条约束一路向上传导，最终成为
  `Handler.OnMessage` 的 `msg` 生命周期约定。

## 测试要求

这一层是唯一面对不可信输入的地方，测试要求相应地严：

**Fuzz（必须）**

```bash
go test -run '^$' -fuzz FuzzCodecParse        # 任意字节 → 不得 panic，不得越界读
go test -run '^$' -fuzz FuzzRoundTrip         # 编码侧：sender 编出来的必须能原样解回来
go test -run '^$' -fuzz FuzzWebSocketFrames   # 见 05
```

`FuzzRoundTrip` 用 fuzz 输入**同时派生配置和消息序列**，以独立的解析实现作为 oracle。
只 fuzz 解码侧会漏掉编码侧的 bug。

**性质测试（必须自证走到了有意思的分支）**

round-trip 断言之外，还要统计线路上到底出现了多少压缩帧、合并帧、加密帧、4 字节头帧，
**任何一类为 0 就直接失败**。少了这一段，一个「所有分支都退化成明文独立帧」的回归会让
round-trip 断言全部通过。

**边界用例（按协议切换点取，不按业务长度取）**

| 边界 | 取值 |
| --- | --- |
| 2/4 字节头切换 | `size = 4095, 4096` |
| 低 16 位进位 | `size = 65535, 65536` |
| 规范编码 | 构造 `m=1, size=100` 的帧，必须被拒 |
| 扩展空间 | 构造 `m=1, 高12=0, 低16=0` 的帧，必须被拒 |
| 空消息 | `size = 0`，含它在 compound 里的计量 |
| 协议上限 | `size = maxMessage, maxMessage+1` |

## 设计决策记录

### W1. 强制规范编码，并用腾出的编码空间做扩展点

**问题。** 上一版一条 100 字节的消息有两种合法线路表示（2 字节头，或 `m=1` 的 4 字节头）。
这是 parser differential 的温床。

**选择。** `m = 1 ⟺ size >= 4096`，违反即协议违规。一次比较的成本。

**收益（不只是消除歧义）。** 这条规则让 `m=1 && 高12==0 && 低16<4096` 变成不可达编码，
凭空得到 4096 个取值作为**唯一的**协议扩展点。原本这份格式是没有任何保留位的
（4 个标记位 + 12 位长度刚好占满 16 bit），加了这条规则反而有了未来。

### W2. 服务端不接受上行压缩与合包

见[上文](#为什么服务端不接受上行压缩与合包)。**收益不存在，代价是两条攻击面**，
所以不是「暂不支持」，而是**明确不支持**。

结果：服务端进程里根本不存在 zstd 解码器。这比「支持但设个上限」强得多——
后者是靠参数防守，前者是攻击面不存在。

### W3. 配了 Cipher 就要求每帧 `e = 1`

见[降级攻击](#降级攻击清掉-e-位)。这是这一版新增的检查，堵掉标记位翻转里唯一那条
**静默**路径（其余三种都会自然导致解析失败）。一次布尔判断。

### W4. 一份 codec，角色差异只体现为 allow 掩码

上一版三处独立实现，三种策略，同一个缺陷在不同传输上以不同形式出现。

**代价。** `codec` 要带一个策略字段，`parse` 里多一次掩码比较（分支预测友好，
实测在噪声内）。

### W5. 先拼包后压缩，而不是逐条压缩

zstd 跨消息复用上下文。这是整份协议里最主要的性能价值点。`Outbound.Dict`
是它的补充而不是替代——有字典之后单条小消息也压得动，两者叠加效果最好。

### W6. 子消息标记位必须全 0

让「不存在嵌套」和「子消息互不可见」成为**结构性事实**而不是纪律：
前者由 `allow = 0` 的子策略保证（展开因此是迭代的），后者由三索引切片保证。

### W7. 计量一律用 `frameSize` 而不是 `len(payload)`

空消息在线路上占 2 字节、在内存里占一个队列条目。按 `len` 计量会让空消息不消耗
任何配额，`Send([]byte{})` 循环可以在配额已设的情况下把队列涨到 OOM。

### W8. `parse` 与 `deliver` 分离

「数据不足」是唯一可重试的返回，它只可能来自 `parse`。分离让这两种语义在类型上
不会纠缠。

## 附：编解码伪码

```
encode(msgs []message, cfg Outbound) → wire bytes
────────────────────────────────────────────────
  分组：连续的可合包消息聚成一组，累计 frameSize 不超过 MaxCluster
  单条成组 → 走独立帧路径

  独立帧：
    data, flag := msg.payload, msg.alreadyFlags
    if 允许压缩 && CompressThreshold > 0 && len(data) > CompressThreshold:
        out := zstd.EncodeAll(data, pooled)
        if len(out) < len(data):          // 压完更大就丢掉压缩结果
            data, flag = out, flag|z
    if cipher != nil && 允许加密:
        data = cipher.Seal(pooled, data)  // Overhead()==0 时原地
        flag |= e
    assert len(data) <= maxMessageSize
    header := encodeHeader(len(data)); header[0] |= flag
    → iovec{header, data}

  compound（组内 >= 2 条）：
    body := Σ (encodeHeader(len(m)) + m)  // 子头标记位全 0
    flag := c
    if CompressThreshold > 0 && len(body) >= CompressThreshold:
        out := zstd.EncodeAll(body, pooled)
        if len(out) < len(body): body, flag = out, flag|z
    if cipher != nil:
        body = cipher.Seal(pooled, body); flag |= e
    assert len(body) <= maxMessageSize
    header := encodeHeader(len(body)); header[0] |= flag
    → iovec{header, body}

decode(src []byte, c codec) → messages
──────────────────────────────────────
  f, n, ok, err := c.parse(src)         // 校验规格 1~10
  if err != nil: 关闭连接
  if !ok: 保留 src，等下一次读事件

  data := f.payload
  if f.e: data = cipher.Open(data)      // 失败 → 关闭连接
  if f.z: data = decompress(data, 上限) // 失败/超限 → 关闭连接
  if f.c:
      sub := c.subCodec()               // allow = 0
      for len(data) > 0:
          g, k, ok, err := sub.parse(data)
          if err != nil || !ok: 关闭连接   // 切不干净 = 协议违规
          deliver(g.payload)
          data = data[k:]
  else:
      deliver(data)
  消费 n 字节
```
