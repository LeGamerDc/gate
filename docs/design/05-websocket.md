# WebSocket

本文定义 WebSocket 传输：它在分层里的位置、握手、入站帧层、出站封帧、关闭语义，
以及**如何保证它与裸 TCP 对业务呈现完全相同的语义**。

最后一条是这一层存在的全部难点。上一版 README 里有这么一句：

> TCP 和 WebSocket 是两套完全独立的入站状态机（`conn.onTraffic` 与
> `wsConnState.onTraffic`），却承诺对业务层呈现相同语义。

于是那份承诺只能靠一个端到端测试矩阵持续验证。这一版把它变成结构性的：
**只有一套 gate 帧循环，WebSocket 只是它前面多了一层字节变换。**

## 分层位置

```
裸 TCP：
   socket 字节 ──────────────────────────────▶ gate 帧循环 ──▶ OnMessage

WebSocket：
   socket 字节 ──▶ WS 帧层（去掩码、控制帧、跳过帧头）──▶ gate 帧循环 ──▶ OnMessage
                          ↑ 每轮读事件调用一次              ↑ **同一份代码**
```

关键在于分工线画在哪里：

- **WS 帧层的职责**：从原始字节里切出 WebSocket 帧，校验帧头，去掩码，
  处理控制帧，然后把**数据帧的 payload** 一段一段喂给下一层。
- **gate 帧循环的职责**：在字节流上解析 gate 帧、维护「不足一帧」的残片、
  检查暂停与关闭、投递给业务。**它不知道字节从哪来。**

于是「两种传输语义一致」不再是一句承诺，而是**同一份代码**。抽象成本是**每轮读事件
一次接口调用**，不是每条消息一次——这个量级完全可以忽略，不需要为它上泛型单态化。

```go
// 内部接口。裸 TCP 的实现是恒等变换。
type inbound interface {
	// feed 把本轮读到的原始字节转换成若干段 gate 字节流，逐段调用 emit。
	// emit 返回 error 表示上层要求停止（暂停 / 关闭 / 协议错误）。
	feed(raw []byte, emit func(payload []byte) error) error
}
```

## 握手

### 自己定位请求边界

```
在缓冲里找 "\r\n\r\n"
  找不到 → 若已积累字节数 > MaxHandshakeBytes 则拒绝，否则等更多数据
  找到   → 把**恰好一个**完整请求交给 HTTP 解析器，消费掉这些字节，剩下的留给帧层
```

**不能把整个缓冲直接扔给解析器。** 常见的 WebSocket 库会在内部套一层带缓冲的
reader，它会预读到自己的缓冲里；用「解析前后的长度差」来推断消耗了多少字节，
得到的数往往大于握手本身的长度，于是**紧跟在握手后面的数据帧字节会被一并吃掉**。

RFC 要求客户端等到 101 之后才发帧，所以合规实现碰不到这个坑；但流水线发送的客户端
（以及任何为了省一个 RTT 而抢跑的实现）会静默丢数据。自己切边界顺带还有一个好处：
数据不足时根本不用调解析器，省掉一次整体重放。

### 大小与数量上限

| 限制 | 值 | 超出行为 |
| --- | --- | --- |
| 单个握手请求字节数 | `WebSocketOptions.MaxHandshakeBytes`，默认 16KB | 拒绝握手 |
| 记录的请求头条数 | 64 | **拒绝握手，不是截断** |
| 握手完成时限 | `Limits.HandshakeTimeout`，默认 10s | 关闭（`ErrHandshakeTimeout`） |
| 并发握手中的连接数 | `Limits.MaxHandshaking` | 拒绝新连接 |

**头条数超限必须拒绝而不是截断。** HTTP 头没有「重要的排在前面」这种保证，
顺序完全由客户端和中间代理决定。静默丢弃意味着攻击者只要在前面塞满 64 条无关头，
`Authorization` / `Cookie` / `X-Forwarded-For` 就对 `OnUpgrade` 不可见——
把「头不存在」当成匿名放行的鉴权逻辑会被直接绕过。**宁可失败，也不要让鉴权基于
一份被悄悄截断的请求头做判断。**

后两条是这一版新增的，堵的是同一个洞：**握手阶段的连接一条完整消息都没交付过，
`Limits.Idle` 根本不认它**。一个慢速发 HTTP 头的客户端可以在任何回收机制注意到它
之前把 fd 耗光——这就是 slowloris 在 WebSocket 上的形态。见
[04 的超时](04-reactor.md#超时与空闲回收)。

### 鉴权在 `OnUpgrade`，不在 `OnOpen`

```go
OnUpgrade: func(h *gate.Handshake) error {
	if h.Header.Get("Authorization") != wantToken {
		return gate.RejectUpgrade(http.StatusUnauthorized, "unauthorized")
	}
	return nil
}
```

`OnUpgrade` 在**写出 101 之前**调用，可以返回一个真正的 HTTP 状态码。
`OnOpen` 发生在 101 **之后**，那时返回 error 只能把一条已经升级成功的连接异常断掉，
对端看到的是一个莫名其妙的断线而不是一个可解释的拒绝。

`RejectUpgrade` 是 gate 自己的构造函数，不泄漏底层 WebSocket 库的类型——
上一版要求业务返回 `ws.RejectConnectionError(...)`，那意味着换库就是一次破坏性升级。

### 握手与可写时机

时序是硬承诺：

```
101 写进 socket
  → 连接状态转为 open（出站闸口打开）
  → OnOpen(c)                       ← 业务第一次拿到 *Conn
  → 处理本轮剩余的入站字节
```

**`OnOpen` 是业务第一次拿到 `*Conn` 的时刻**，所以在它之前**不可能有任何消息入队**。

这条时序消掉了上一版一整块机制：那时 handler 在连接建立阶段就被构造出来，可以在
握手完成前 `Send`，于是出站层必须支持「连接不可写时把消息留在队列里且不 arm 唤醒」，
还要在握手完成时补一次主动排空（并因此需要一个 `flushHook` 来绕开类型断言失败的问题）。

现在这些全部不需要——**不可写时不可能有消息入队**，见
[03 的不变式 O11](03-outbound.md#不变式清单)。

## 入站帧层

### 不做分片重组

这是这一层最重要的一个简化。

一条被分片的 WebSocket 消息 = `[FIN=0, binary, P1]` + `[FIN=1, continuation, P2]`，
它承载的 gate 字节流就是 `P1 || P2`。而 gate 帧本身是**自定界**的，
下一层已经维护着「不足一帧的残片」。

所以：**把每个数据帧的 payload 直接喂给 gate 帧循环就行了，`P1`、`P2` 分两次喂
和一次喂完全等价。** 一个跨分片的 gate 帧会被残片机制自然接上。

WS 帧层因此**不需要任何重组缓冲**，只需要一个布尔标记来做协议校验
（「是否处在一条分片消息中间」）：

| 情况 | 处理 |
| --- | --- |
| `binary`，`FIN=1` | 直接喂下去 |
| `binary`，`FIN=0` | 喂下去，标记进入分片状态 |
| `continuation`，分片状态中 | 喂下去；`FIN=1` 则退出分片状态 |
| `continuation`，非分片状态 | 协议违规 |
| `binary`，分片状态中 | 协议违规 |
| 控制帧（分片状态中也允许穿插） | 单独处理，不影响分片状态 |

上一版有一个每连接的 `fragmentBuf`（一个 `bytes.Buffer`），会积累到整条消息收全为止——
上限是 `MaxMessage`。去掉它意味着**每连接少一块可能涨到几十 MB 的缓冲**，
也少一处需要「空闲时收缩」的内存。

### 一次读事件的处理

```
feed(raw):
    data := 残片 + raw            ← WS 级残片：上一轮留下的半个 WS 帧
    loop:
        解析 WS 帧头 → 不足则 break
        校验（见校验清单）
        payload := data[头长 : 头长+长度]
        若不足一个完整帧 → break
        去掩码（**原地**，就在读缓冲上）
        控制帧 → 单独处理
        数据帧 → emit(payload)     ← 交给 gate 帧循环
        data = data[帧长:]
    剩下的 data → 存进 WS 级残片
```

**去掩码是原地做的**，直接在每 loop 的读缓冲上异或，不产生任何拷贝。

**控制帧的长度校验必须在「数据够不够一个完整帧」之前。** RFC 6455 §5.5 规定控制帧
payload 不得超过 125 字节。放在后面判的话，一个声称自己带 32MB payload 的 `ping`
会让我们老老实实把字节攒进残片缓冲，一直攒到撞上上限才失败——每条连接白白吃掉几十 MB，
而按 RFC 判的话读到帧头第二个字节就能拒掉。

### 两块残片，各自的上界

| 残片 | 内容 | 上界 |
| --- | --- | --- |
| WS 级 | 不足一个完整 WS 帧的尾巴 | 一个 WS 帧 = `MaxMessage` + 帧头 |
| gate 级 | 不足一个完整 gate 帧的尾巴 | `MaxMessage`（`Pause` 时是 `MaxPending`） |

两块**稳态下都是空的**：对端发的是完整帧时，读缓冲里的字节当轮就被消费干净。
它们都从分级池借，用完归还，不挂成连接的常驻字段。

> 上一版这里有三块每连接的 `bytes.Buffer`（原始字节、解出的 gate 字节、分片重组），
> 而且因为它们是常驻字段，还需要一套「连续 N 轮空闲后把超大缓冲还给 GC」的收缩逻辑。
> 现在残片从池里借、稳态为空，那套收缩逻辑整个不需要了。

## 出站封帧

```
flush 攒好一批 gate 帧的 iovec
  → 计算总字节数
  → 在最前面插一个 WS 二进制帧头（2~10 字节）
  → 一次 writev 全部发出
```

**一次 `writev` 的一整批 gate 帧装进一个 WS 二进制帧**，而不是每条 gate 帧一个 WS 帧。
gate 帧本身自定界，外层用一个 WS 帧就够；这样 WS 帧头的开销从「每条消息 2~10 字节」
降到「每批 2~10 字节」。

一次 flush 因 `IOV_MAX` 拆成多次 `writev` 时，每一批各自成为一个 WS 二进制帧——
合法，对端把它们的 payload 首尾相接就还原成同一个 gate 字节流。

服务端帧**从不带掩码**，所以帧头最长 10 字节（2 字节基础头 + 8 字节扩展长度），
用不到带掩码的 14 字节。

帧头暂存和 iovec 一样是**每 loop 一份**，不挂在连接上：它只在一次写调用期间有用，
而所有出站写都发生在连接自己的事件循环上且中途不让出，所以池里同时在外的对象数
等于事件循环数，不随连接数增长。挂成连接级字段的话，10 万连接光这一块就要白占
一百多 MB。

### 部分写与 WS 帧头

WS 帧头一旦写出去，长度就是承诺过的——必须**恰好**再发那么多字节。
[03 的 stage 2](03-outbound.md#stage-2待发送链) 保证了这一点：
帧头和 payload 都是链上的 chunk，部分写只推进 `off`，内容一个字节都不会变。

## 关闭语义

### 收到对端的 close 帧

回一个 close 帧完成握手，然后关闭 TCP，`OnClose(c, ErrPeerClosed)`。

注意常见 WebSocket 库的一个坑：它们的 close 处理函数在写完响应之后**总是**返回一个
非 nil 的「已关闭」错误——**正常关闭（1000）也不例外**，那是它报告「对端关闭了」的
方式，不是错误。不翻译这一种的话，每一次正常断开都会打一条 warn 日志；连接数一大
就是纯刷屏。但**真正的协议违规**（非法的 close code、非 UTF-8 的 reason）必须留在
错误路径上，所以只能翻译「已关闭」这一种，不能一律吞掉。

### 本地主动关闭

上一版一律直接关 TCP，对端看到的是 1006（abnormal closure）——**分不清「被踢了」
和「网络断了」**。这一版按关闭原因区分：

| `reason` | close code | 发不发 close 帧 |
| --- | --- | --- |
| `nil`（正常）、业务自定义 error | 1000 normal | **发** |
| `ErrServerClosed` | 1001 going away | **发** |
| `ErrIdleTimeout`、`ErrPauseTimeout`、`ErrHandshakeTimeout` | 1001 going away | **发** |
| `ErrProtocol` | 1002 protocol error | **发** |
| `ErrPendingOverflow`、消息超限 | 1009 message too big | **发** |
| `ErrHandlerPanic` | 1011 internal error | **发** |
| `ErrBackpressure`、底层写失败 | —— | **不发**，直接关 TCP |

最后一行的理由：出站方向已经写不动了（这正是 `ErrBackpressure` 的定义），
再排一个 close 帧只会跟着卡住。写失败同理——帧流已经有洞了。

close 帧是**尽力发送**的：它排在出站队列尾部，`Outbound.CloseLinger` 到期就放弃。
不能为了发一个 close 帧无限期占着 fd。

## 与 TCP 的语义对齐

业务代码在两种传输下**一行都不用改**。逐条对齐：

| 语义 | 两种传输如何一致 |
| --- | --- |
| `OnMessage` 看到的是完整单条业务消息 | 同一个 gate 帧循环 |
| 一次「事件」里可以有多条消息 | TCP 是一个读事件，WS 是一个（或多个）数据帧；都由同一个循环展开 |
| `OnMessage` 返回 error 停止本批投递 | 循环在同一处检查 |
| `Pause` 期间不投递 | 同上 |
| `msg` 只在本次调用内有效 | 同一份残片管理 |
| `Limits.MaxMessage` 的口径 | 都是 gate 帧的 payload 长度 |
| 活跃判据 = 交付完整消息 | 同一个交付点 |
| 协议错误一律关闭连接 | 同一套错误分类 |
| `OnOpen` 时连接一定可写 | TCP 在 socket 就绪后，WS 在 101 之后 |

**唯一对业务可见的差异**是 `c.Handshake()`：WebSocket 下返回握手信息，TCP 下返回 nil。

尽管一致性现在是结构性的，测试矩阵仍然保留——它现在验证的是**边界**
（WS 帧长度切换点、分片、控制帧穿插），而不是「两份实现有没有漂移」。
尺寸边界要按各自协议的切换点取：WS 帧头的宽度切换点是按 **WS 载荷**算的，
而 WS 载荷 = gate 帧头 + 业务长度，中间差 2 或 4 字节。所以覆盖 WS 的 126 边界
要用业务长度 123 / 124，覆盖 65536 边界要用 65531 / 65532。这组用例还必须关掉压缩
——否则线路上的长度由 zstd 决定，精心挑出来的边界值一个都落不到。

## 每连接内存

| 项 | 握手期 | 握手后 |
| --- | --- | --- |
| HTTP 解析临时状态、升级回调闭包 | 有 | **立刻释放** |
| `Handshake`（URI + 请求头） | 有 | 保留（业务要读） |
| WS 级残片 | 稳态 0 | 稳态 0 |
| 分片重组缓冲 | —— | **不存在**（不做重组） |

握手完成后必须**主动放掉握手期的全部状态**：解析器、升级回调、以及它们捕获的闭包
环境。上一版这些跟着连接活到关闭为止，每条 WebSocket 连接都白白钉住一组闭包。

`Handshake` 里的 `http.Header` 是留给业务的，会活到连接关闭。它是一个 map，
64 条头就是 64 个 map 项加 64 个切片——10 万连接下不是零头。需要极致内存的部署
可以在 `OnUpgrade` 里把关心的字段抽进 `State`，gate 提供的是完整的那份。

## 不允许的 WebSocket 特性

| 特性 | 为什么不支持 |
| --- | --- |
| `permessage-deflate` | gate 在 gate-帧层已经有压缩（而且是先拼包再整体压，效果更好）。再套一层等于双重压缩，只增加 CPU。**握手响应里绝不能协商它**——客户端提议了却被静默当成接受，会导致双方对字节流的理解不一致 |
| `text` 帧 | gate 的 payload 是二进制。收到 `text` 按协议违规关闭，而不是尝试解释 |
| 子协议协商 | 响应里不返回 `Sec-WebSocket-Protocol`。客户端提供的原始值仍会记进 `Handshake`（浏览器常用它携带 token），但 gate 不做协商 |
| 扩展（`Sec-WebSocket-Extensions`） | 一律不协商 |
| `wss` | 前置代理终结，见 [01 的非目标](01-server-api.md#非目标) |

## 校验清单

入站帧的校验顺序（顺序本身是规格的一部分）：

```
1. 帧头字节不足                          → 等更多数据
2. RSV != 0                              → 协议违规   ← 我们不协商任何扩展
3. opcode 是保留值                        → 协议违规
4. opcode == text                        → 协议违规
5. 控制帧且 payload > 125                → 协议违规   ← 必须早于“数据够不够”
6. 控制帧且 FIN == 0                     → 协议违规
7. 长度 > MaxMessage                      → 协议违规
8. 客户端帧未带掩码                       → 协议违规
9. 数据不足一个完整帧                     → 等更多数据
10. 去掩码（原地）
11. 分片状态校验（见入站帧层的表）
12. 控制帧 → 处理；数据帧 → emit
```

第 5 步的位置见[上文](#一次读事件的处理)。第 8 步是 RFC 的硬要求：
服务端必须拒绝未掩码的客户端帧。

## 不变式清单

| # | 不变式 |
| --- | --- |
| W1 | 只有一份 gate 帧循环，两种传输共用；WS 层只做字节变换 |
| W2 | 不做 WS 分片重组——gate 帧自定界，残片机制自然接上 |
| W3 | 101 写出 → 状态转 open → `OnOpen`。`OnOpen` 之前不可能有消息入队 |
| W4 | 鉴权在 `OnUpgrade`（101 之前），`OnOpen` 只做初始化 |
| W5 | 请求头超过 64 条**拒绝握手**，绝不截断 |
| W6 | 控制帧长度校验早于「数据够不够一个完整帧」 |
| W7 | 一次 `writev` 的一批 gate 帧 = 一个 WS 二进制帧 |
| W8 | 去掩码原地进行，不产生拷贝 |
| W9 | 握手完成后立刻释放握手期的解析状态与回调闭包 |
| W10 | 正常关闭发 close 帧并带状态码；背压与写失败直接关 TCP |
| W11 | 绝不协商 `permessage-deflate` / 子协议 / 任何扩展 |

## 设计决策记录

### W-D1. 一份 gate 帧循环，WS 只是前置的字节变换

**问题。** 上一版是两套完全独立的入站状态机，却承诺对业务呈现相同语义。
一致性只能靠测试矩阵持续验证，任何一边的改动都可能让另一边悄悄漂移。

**选择。** 把分工线画在「谁维护 gate 帧的残片」上：gate 帧循环维护它，
WS 层只负责把原始字节变成一段段 gate 字节流。于是两种传输共用同一份投递代码。

**代价。** 每轮读事件一次接口调用。不是每条消息一次——这个量级可以忽略，
不需要为它上泛型单态化。

**收益。** 「语义一致」从承诺变成事实；测试矩阵的职责从「查漂移」升级为「查边界」。

### W-D2. 不做分片重组

一条分片消息承载的 gate 字节流就是各分片 payload 的拼接，而 gate 帧自定界、
下层已经有残片机制。**每连接少一块可能涨到几十 MB 的重组缓冲**，
也少一处需要「空闲时收缩」的内存管理。

WS 层只保留一个布尔标记用于协议校验（是否处在分片消息中间）。

### W-D3. `OnOpen` 在 101 之后，因此不可写时不可能有消息入队

上一版 handler 在连接建立阶段就被构造，可以在握手完成前 `Send`，于是出站层必须支持
「不可写时留在队列里且不 arm 唤醒」，还要在握手完成时补一次主动排空，并因此需要一个
内部钩子来绕开「业务用 wrapper 包住 sender 会让类型断言失败」的问题。

把 `OnOpen` 挪到 101 之后，这些**全部不需要**：业务第一次拿到 `*Conn` 时连接已经可写。

### W-D4. 鉴权在 `OnUpgrade`，不在 `OnOpen`

`OnOpen` 在 101 之后，那时拒绝只能异常断线。`OnUpgrade` 能返回真正的 HTTP 状态码。
分工写清楚，避免业务把鉴权写在错误的钩子里。

### W-D5. 请求头超限拒绝而不是截断

HTTP 头没有「重要的排在前面」这种保证。静默截断意味着攻击者塞满无关头就能让
`Authorization` 对鉴权钩子不可见。**宁可失败，也不要让鉴权基于一份被悄悄截断的
请求头做判断。**

### W-D6. 本地关闭发 close 帧，按 reason 映射状态码

上一版一律直接关 TCP，对端只能看到 1006，分不清「被踢了」和「网络断了」。
成本是一个小写操作，收益是客户端能做出正确的重连决策（被踢就别重连了）。

例外是背压和写失败——那两种情况下出站方向本来就写不动或已经有洞，
排一个 close 帧只会跟着卡住。

### W-D7. 明确拒绝 `permessage-deflate`

gate 在 gate-帧层已经有压缩，而且是先拼包再整体压，效果比 WS 层逐消息压更好。
关键是**握手响应里绝不能协商它**：客户端提议了却被静默当成接受，双方对字节流的
理解就不一致了。

### W-D8. 不泄漏底层 WebSocket 库的类型

`RejectUpgrade(status, reason)` 是 gate 自己的构造函数。上一版要求业务返回
底层库的错误类型才能自选状态码——那意味着换库就是一次破坏性升级。
同 [01 的 D7](01-server-api.md#d7-底座类型不出现在公共-api)。
